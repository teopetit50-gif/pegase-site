### 3.2 La répétition : sur quelle copie, et ce qu'elle coûte

**Voie retenue : GitHub Actions, gratuite.** Une base `supabase/postgres:17.6.1.155` (la version exacte de la
production) est remise « comme la production » par le relevé du 23/10 (`base/01_extensions.sql`,
`02_schema.sql`, `03_crons.sql` : schéma sans aucune donnée), plus `base/00_services_supabase.sql` (ce que Storage
et Auth créent dans une vraie base, forme relevée dans le catalogue de la production). Puis les 464 fichiers, un
par transaction, **en rôle `postgres`** comme en production (le relevé aussi : en production `postgres` possède
`public`, `private` et tous leurs objets, sans être superutilisateur), avec les droits par défaut de la production ; pg_cron et pg_net coupés, rien ne sort.

```bash
git tag repetition-AAAAMMJJ && git push origin repetition-AAAAMMJJ
```

Résultat dans GitHub → Actions → « Répétition du SQL (Postgres jetable) » ; sans `gh`, les annotations se lisent par
l'API publique (`/repos/teopetit50-gif/pegase-site/check-runs/<id>/annotations`). Durée : 3 min. Coût : 0 €.
Le tag `repetition-*` ne vaut pas gel ; `prod-*` aussi déclenche la répétition et vaut gel.

En local (si GitHub est indisponible) : `bash omega/prod/repetition-locale.sh` — Docker (colima), 2 Go d'image,
4 à 6 Go de mémoire : **jamais en même temps qu'une autre session lourde** (le Mac de 8 Go a planté le 25/10).

**Ce que la répétition ne couvre pas : les données.** Une migration qui ajoute une contrainte, une colonne `not null`
ou un index unique passe sur des tables vides et peut échouer sur de vraies lignes. La production n'a que les
données du site d'avant (pas de client Omega) ; pour l'éprouver quand même, `poser-palier.sh Pn --essai` joue le
palier **sur la production dans une transaction annulée** (§ 4.1). Voies payantes écartées : une branche Supabase
(`create_branch`) rejoue les migrations du dépôt **sans les données** et ne vaut pas mieux que la répétition gratuite ;
restaurer la sauvegarde dans un projet jetable coûte un projet facturé à l'heure (prix à demander par `get_cost`
avant, avec l'accord de Teo). Ni l'une ni l'autre n'a été créée.

  secondes à quelques minutes) : à faire dans la fenêtre. Un essai rouge ne pose rien : on s'arrête et on corrige

- Sans option : chaque fichier dans sa transaction, avec sa ligne `schema_migrations` (version, nom, sha256 du
  fichier) ; arrêt au premier échec ; un fichier déjà inscrit est sauté (on relance après correction).
  `lock_timeout` 10 s : un verrou tenu par le site fait échouer proprement le fichier au lieu de bloquer le site.

### 4.3 Si un palier casse

1. Le fichier fautif n'a rien posé (transaction). Les précédents sont posés et inscrits.
2. Lire l'erreur, reproduire sur la répétition (`repetition-*`), corriger l'export (jamais le SQL à la main en
   production), recommiter, relancer `poser-palier.sh` sur le même palier : les fichiers inscrits sont sautés.
3. Si le site va mal (§ 7.2) : `cron.alter_job(…, active := false)` sur les crons du palier ; pour des données
   abîmées seulement, restauration de la sauvegarde du § 1.2.

### 5.4 La clé IA : écart à la promesse « données en Europe »

Décision de Teo du 25/10 : **l'API Anthropic directe** pour l'instant, pas AWS Bedrock. Le code choisit l'API
directe dès que `ANTHROPIC_API_KEY` est posée, sinon Bedrock (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`,

**À régler avant le premier vrai client** : soit Bedrock en Europe (retirer `ANTHROPIC_API_KEY`, poser les secrets
AWS : aucun code à changer), soit modifier la promesse et le registre des traitements. Même remarque pour la
reconnaissance vocale de Twilio (voie « twilio » de reput-appels, hors UE).

## 9. Risques pour omegaai.fr, et comment les éviter

| Risque | Quand | Parade |
|---|---|---|
| **Le site d'avant cassé par un lot de droits** (19e, 19k, a5_01 touchent tout `public` ou tout `private`) | P2, P3, P6 | vérifié : aucun fichier ne crée, ne modifie ni ne supprime une table ou une fonction du site ; 19e retire `truncate/references/trigger` (sans effet) ; 19k **ajoute** des droits à `authenticated` sur une table dont une politique les suppose ; a5_01 ne touche que `private`. Tester après P3 et P6 : réservation d'audit, commande, espace client |
| Un verrou long sur une table que le site lit | P2-P5 | `lock_timeout` 10 s dans `poser-palier.sh` ; fenêtre du soir ; l'essai annulé fait la même chose : à faire dans la fenêtre aussi |
| Un lot échoue sur de vraies données (contrainte, `not null`, index unique) | P1-P5 | `--essai` avant chaque palier ; un fichier en échec ne pose rien |
| Des écrans de `main` appellent déjà des fonctions absentes : 39 RPC (`annuaire`, `grp_*`, `lorani_*`, `tiroma_*`, `messagerie_*`, `reception_marquer`, `filed_cycle_vie_facture`…) et ~100 tables (`btp_*`, `cashd_*`, `filed_*`, `grp_*`, `loc_*`, `lorani_*`, `reput_*`, `tamila_*`, `receptions`, `messageries`…) | **aujourd'hui** | la pose les répare ; d'ici là ces pages de `/espace2` sont vides ou en erreur en production |
| Un écran fusionné avant la base | F | fusion seulement après P6 et § 5 ; aucune branche à fusionner n'appelle autre chose que ce que la recette a, sauf Daliro (`btp_avenants_photos`) |
| Crons qui appellent une fonction absente | P3 → § 6 | sans `cle_service` au Vault, ils n'appellent rien ; poser le Vault après les fonctions |
| Une fonction Edge appelle la recette | § 5-6 | aucune coquille ne nomme la recette ; `reput_reponse_url` réécrit (§ 6) ; contrôle `like '%ygwbgpowzlbdaajlsqkn%'` sur `cron.job`, `pg_proc` et `private.reglages` |
| Envois réels à des tiers dès la pose | § 5-6 | aucun client Omega en production : rien à envoyer ; les réglages d'envoi des futurs clients naissent en `coupe`/`essai` (19ah) |
| Données hors UE | dès la clé IA | § 5.4, à régler avant le premier client |
| Realtime : 46 tables publiées d'un coup | P2-P5 | charge négligeable sans clients ; surveiller l'usage Realtime de Supabase la première semaine |

Les fonctions existantes du site ne changent pas | P3, P5, P6 | **décision de Teo** : l'accepter (conseillé : toutes les portes ont été éprouvées ainsi) ou retirer ce bloc d'a5_01 et poser un `grant` explicite par porte |
